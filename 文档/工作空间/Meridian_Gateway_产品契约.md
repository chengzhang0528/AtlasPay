本文是 Meridian Gateway 当前产品行为和业务边界的唯一长期事实所有者。原规划文档保留为本次实施输入；与已验证源码或测试冲突时，以本契约明确的行为为准，并在同一变更中修正冲突。

## 产品定位

Meridian Gateway 是商户自行部署的支付连接服务。服务统一订单、支付状态、渠道凭证、回调、退款、费用和对账；资金始终由商户自己的支付账户清结算，系统不持有余额、不代收、不换汇、不自动清分。

## 部署与接入边界

- 默认由一个 Docker 容器运行一个 Go 服务进程，使用持久卷中的 SQLite WAL 数据库，不依赖 Redis、MQ、Vault 或独立管理服务。
- 管理后台、消费者收银台、REST API、OpenAPI 和后台任务均由同一二进制提供。
- 商户系统只依赖 HTTPS、REST、JSON、API Key 和签名 Webhook，不暴露渠道专属状态或内部凭证。
- 主密钥来自运行环境；渠道私钥、Webhook 密钥等敏感值必须加密持久化，日志和 API 响应不得回显。
- 生产镜像必须从本仓库源码构建；服务不得向第三方遥测或控制中心发送业务数据。只有管理员明确选择支付宝官方沙箱时，测试订单才发送至该官方环境。

## 租户与身份

- 系统管理员使用部署环境中的全局管理令牌创建商户，并可为商户签发仅显示一次的高熵管理令牌；商户管理令牌只能访问自身资源，不能创建商户或签发管理令牌。
- 商户或系统管理员可在自身授权范围内创建应用；每个应用生成仅显示一次的 API Key 与 Webhook 签名密钥。
- 全局管理令牌不持久化；商户管理令牌和 API Key 只以不可逆摘要持久化。管理操作和商户 API 必须使用不同身份入口，应用 API Key 不得作为浏览器管理身份。
- 所有二维码、订单、凭证、退款、费用、投递和审计查询必须受 merchant_id 约束；跨商户资源一律表现为不可访问。

## 统一订单规则

- 金额使用最小货币单位整数；V0.1-V0.3 默认只接受 CNY，金额必须大于零。
- 同一应用内 merchant_order_id 唯一；相同关键字段重试返回原订单，不同字段复用同一编号返回冲突。
- 状态主链为 created -> pending -> paid；pending 可进入 failed 或 closed；paid 可进入 refunding、partially_refunded 或 refunded。
- 任何支付成功只接受操作员人工确认，或支付宝已验签异步通知/主动查询。消费者回跳、倒计时结束、截图或前端请求不能直接置为 paid。
- 本地有效期只控制是否继续展示或提交支付；只要订单尚未得到支付宝关闭确认，之后到达的已验签成功通知或主动查询结果仍必须记为 paid。只有渠道已确认关闭的订单保持 closed。
- 每次状态变化保留操作者、时间、原因、渠道状态和最近错误；重复、乱序事件不得重复计费或重复生成商户事件。

## 版本能力

### V0.1 静态收款码

- 商户配置支付宝账户标识，上传按门店区分的静态二维码并启停。
- 商户创建 static_alipay 订单后获得独立收银地址；页面明确标记人工确认。
- 操作员确认到账时，订单、费用、审计和商户 Webhook Outbox 在同一数据库事务中形成。
- 操作员可标记异常；异常不等于支付成功。

### V0.2 动态二维码

- alipay_qr 订单调用商户自己的支付宝应用，支持预创建、主动查询、异步通知、超时关闭、全额或部分退款和对账导出。
- 支付宝账户只接受 `sandbox` 或 `production` 环境以及 App ID、应用 RSA2 私钥和支付宝 RSA2 公钥；官方网关由环境确定，Notify URL 由 `MERIDIAN_BASE_URL` 派生。
- 管理端必须按所选环境提供支付宝官方沙箱/应用控制台、RSA2 密钥工具、接口加签设置和正式产品开通入口，解释应用私钥、应用公钥与支付宝公钥的去向，并在保存前展示派生的 Notify URL 和公网 HTTPS 条件，使未培训商户可按页面步骤独立完成配置。
- 请求、通知和商户 Webhook 均具备幂等性；签名错误、重复/乱序通知和渠道超时必须可观察。
- 二维码过期后先查询支付宝状态，再关闭仍待支付的渠道订单；渠道未建单可本地关闭，传输失败使用持久化有上限指数退避，不得按 worker 扫描频率持续请求。
- 支付宝成功通知或主动查询保存 `trade_no`；付款完成不依赖浏览器停留。

### V0.3 支付跳转

- alipay_page 和 alipay_wap 复用同一订单模型和支付宝账户，返回可信的跳转地址或自动提交表单。
- return_url 只展示查询结果；未提供时使用 Meridian 只读结果页，最终状态仍来自已验签通知或主动查询。
- 中断后可凭收银地址恢复；终态或本地过期订单不得继续展示二维码或提交跳转，成功页和失败页不得改变订单状态。

### 退款恢复

- 每个 `merchant_refund_id` 固定映射为支付宝 `out_request_no`；进行中、完成后和全额退款后的同号重试返回原退款记录。
- 支付宝传输超时、响应验签失败或不确定业务错误不得直接记为 failed；退款保持 pending、订单保持 refunding，并按持久化退避执行退款查询，查询不存在时才使用同一 `out_request_no` 重试。
- 新退款在调用渠道前即设置恢复期限，进程在渠道调用前后退出都能由 worker 接管；明确业务拒绝才恢复订单为 paid 或 partially_refunded。

## Webhook 与费用

- paid、closed、refund.updated 等商户事件写入 Outbox 后异步投递；使用应用 Webhook 密钥对时间戳和原始正文做 HMAC-SHA256 签名。
- 投递保存响应状态、尝试次数、下次重试时间和最后错误；成功后停止，失败按有界退避重试。
- 商户可修改自身应用的 Webhook URL、启停应用并轮换 API Key 与 Webhook 密钥；新凭证只显示一次，轮换后旧凭证立即失效。
- 配置有效 Webhook 后，商户可把自身 skipped、failed 或 exhausted 投递重新排队；delivered 事件不得从该入口重放，跨商户投递不得访问。
- 费用规则在确认支付时快照化；同一订单不得重复生成费用记录。

## 明确非目标

- V0.1-V0.3 不接微信或全球多渠道，不做钱包、余额、充值、分账、换汇、订阅、智能路由、截图识别、微服务、Kubernetes 或多实例高可用。
- V0.1-V0.3 不支持支付宝证书模式、自定义支付宝网关或手工覆盖支付宝 Notify URL。
- V0.1-V0.3 不提供用户密码、验证码、找回流程、团队或细粒度 RBAC；管理身份使用全局或单商户高熵令牌。
- 不以模拟渠道结果替代真实支付宝沙箱/正式账号的渠道验收。
- 不承诺在本阶段选择开源许可证、发布公网服务或保存任何真实凭据到仓库。

## 验收原则

- 无渠道凭据时，静态闭环、租户隔离、幂等、持久化、签名、状态机、Outbox 和支付宝适配器合同由自动化测试与本机操作验证。
- V0.2/V0.3 的真实支付、退款和通知闭环只有在用户提供本机 git-ignored 凭据后才可标记通过。
- 自动化白盒验收可以在真实渠道延期时独立完成，但不得据此声称支付宝真实付款、通知或退款已经通过。
- 任何验证不得把密钥、客户数据、原始渠道日志或生成物写入 Git。
